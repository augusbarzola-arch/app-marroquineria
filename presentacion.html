El Problema y Nuestra Solución

El Problema en la PYME
  • Control manual de stock (planillas Excel, papel)
  • Mercadería perdida y descuadres de inventario
  • Devoluciones no controladas con inconsistencias contables
  • Sin visibilidad de métricas en tiempo real
Nuestra Solución
  • Base PostgreSQL centralizada con 13 tablas en 3FN
  • Integridad enforceada por la BD (triggers y FKs)
  • Módulos: POS táctil, Dashboard analítico, Reportes
  • Web responsive con modo oscuro y feedback inmediato
Guion Hablado (Integrante 1): "En una marroquinería existen productos con múltiples variantes (color, material, tamaño). La solución fue construir un sistema donde la base de datos se protege a sí misma, impidiendo inconsistencias sin importar cómo se acceda a los datos."
Augusto Barzola

Entidades Principales

Entidades de Detalle

Tablas de Dominio

Puntos de rigor relacional implementados:

• Claves primarias compuestas en detalles: (id_venta, renglon_venta) y (id_compra, renglon_compra).
• Restricciones CHECK para validar cantidades > 0 y precios positivos.
• Constraints UNIQUE para evitar variantes duplicadas y códigos de SKU repetidos.
Guion Hablado (Integrante 1): "El DER cuenta con 13 tablas separadas limpiamente en maestras, detalles transaccionales y dominios. Las tablas de detalle usan claves primarias compuestas, garantizando renglones unívocos por comprobante."
Augusto Barzola

Normalización en Tercera Forma Normal (3FN)

El diseño erradica redundancias e inconsistencias respetando los principios formales:

Forma Regla Formal Aplicación en el Proyecto
1FN Atributos atómicos, sin listas o grupos repetitivos. Cada variante almacena un único valor por atributo.
2FN Atributos dependen de la clave primaria completa. En detalles compuestos, precio y cantidad dependen del renglón completo.
3FN No existen dependencias transitivas (A → B → C). Color, material y tamaño tienen sus propias tablas referenciadas por ID.
Guion Hablado (Integrante 1): "Demostramos que la normalización no es solo teoría: al aislar colores o materiales en tablas satélites, evitamos anomalías de actualización. Renombrar un color requiere un solo UPDATE, sin tocar millones de ventas históricas."
Augusto Barzola

Triggers — La Base de Datos se Protege a Sí Misma

Automatización transaccional nativa con PL/pgSQL:

CREATE OR REPLACE FUNCTION actualizar_stock_venta() RETURNS TRIGGER AS $$ BEGIN UPDATE variante_producto SET stock_actual = stock_actual - NEW.cantidad WHERE id_variante = NEW.id_variante; RETURN NEW; END; $$ LANGUAGE plpgsql; CREATE TRIGGER trigger_stock_venta AFTER INSERT ON detalle_venta FOR EACH ROW EXECUTE FUNCTION actualizar_stock_venta();
* Análogamente, detalle_compra cuenta con su trigger inverso para sumar stock al ingresar mercadería.
Guion Hablado (Integrante 1): "Uno de los puntos clave del examen: la actualización de stock NO se delega al frontend ni al backend. Si alguien inserta una venta directamente desde consola SQL o un script batch, el trigger garantiza la actualización atómica del inventario."
Augusto Barzola

Diseño Crítico: Integridad en Devoluciones (FK Compuesta)

¿Cómo evitar devoluciones fraudulentas o 'fantasma'?

CREATE TABLE devolucion ( id_devolucion SERIAL PRIMARY KEY, id_venta INTEGER NOT NULL, renglon_venta INTEGER NOT NULL, cantidad_devuelta INT CHECK (cantidad_devuelta > 0), -- FK COMPUESTA: CONSTRAINT fk_devolucion_detalle FOREIGN KEY (id_venta, renglon_venta) REFERENCES detalle_venta(id_venta, renglon_venta) );
¿Por qué no una FK simple a id_venta?

Una FK simple validaría que la venta existe, pero permitiría registrar la devolución de un producto que jamás formó parte de ese ticket.

Garantía: La clave foránea compuesta obliga al motor a validar la existencia exacta del renglón vendido.

Guion Hablado (Integrante 1): "Este es un punto de alta valoración en la cátedra: modelamos la relación con detalle_venta a través de una foreign key compuesta sobre (id_venta, renglon_venta). El motor rechaza físicamente cualquier intento de devolver un ítem inexistente en esa venta."
Augusto Barzola

Consultas Complejas y Álgebra Relacional (Push-Down)

Optimización formal modelada mediante árboles de álgebra relacional:

❌ Árbol Ineficiente (Filtro Tardío)
π (nombre, total_vendido) | γ (SUM por producto) | σ (fecha = HOY) <-- FILTRO AL FINAL | ⋈ JOIN (Todas las tablas)
✅ Árbol Optimizado (Push-Down)
π (nombre, total_vendido) | γ (SUM por producto) | ⋈ JOIN / \ σ (fecha=HOY) detalle_venta | venta <-- Filtro empujado a la hoja
Guion Hablado (Integrante 1): "Aplicamos la regla heurística de Push-Down de selecciones: bajar la condición sigma (fecha = hoy) lo más cerca posible de las hojas. De este modo, los JOINs operan sobre conjuntos de datos reducidos, minimizando memoria y tiempo de CPU."
Augusto Barzola

Decisión de Arquitectura: SQL Directo vs ORM

¿Por qué NO un ORM (SQLAlchemy / Django)?
  • Genera 'queries fantasma' N+1 difíciles de prever.
  • Oculta el control fino de transacciones (BEGIN/COMMIT).
  • Agrega una capa pesada de abstracción innecesaria para un proyecto de Bases de Datos.
Ventajas de psycopg2 directo:
  • Control absoluto del plan de ejecución SQL.
  • Manejo explícito de bloqueos y cursores (RealDictCursor).
  • Pool de conexiones thread-safe con ThreadedConnectionPool.
  • Demostración pedagógica del dominio de SQL puro.
Guion Hablado (Integrante 1): "Elegir psycopg2 directo nos permitió demostrar dominio pleno del estándar SQL y las capacidades del motor. Gestionamos conexiones mediante un ThreadedConnectionPool y delimitamos transacciones explícitas."
Lucas Duarte
